# Git Flow

## Daily Work

- Keep diffs scoped to the confirmed task.
- Do not commit unless explicitly asked.
- Do not amend, rebase, reset, or force-push unless explicitly asked.
- Do not revert unrelated user changes.

## Before Work

- Every implementation task must have a numbered issue. If no issue ID exists, stop and ask the user to create or identify the issue before changing repository files.
- After the issue ID is confirmed, create `feat/{issue-id}` from the latest `main` before editing. Do not implement directly on `main`.
- Changes limited to repository governance (`AGENTS.md`, `.agents/rules/`, or `.agents/skills/`) are exempt from the issue and branch requirements. Keep them in a dedicated commit and never mix them with product changes.

## Commit Messages

- When work belongs to a numbered issue, every non-merge commit must use:
  `<type>(<issue-id>): <imperative summary>`.
- `issue-id` is the parent issue number, not a task-breakdown suffix. For
  example, work in `task-815-0.md` uses scope `815`, not `815-0`.
- Allowed types are `feat`, `fix`, `refactor`, `test`, `docs`, `chore`, and
  `ci`. Choose the type that describes the commit itself, not the whole issue.
- Keep the summary concise, lowercase, imperative, and without a trailing
  period.
- Examples:
  - `feat(815): add timeline feature tables`
  - `test(815): cover timeline migration constraints`
  - `docs(815): document timeline schema`
- Merge commits generated by the hosting platform and automated release commits
  are exempt.
- Do not start implementation or create commits without a numbered issue.
- For the governance exception above, use the existing Conventional Commit form:
  `<type>: <imperative summary>`.

## PR Readiness

- A PR body is a summary plus reviewer notes. Nothing else — no validation, risk, or rollback sections.
- Write the summary in product terms and keep it to at most 5 lines; no file paths, function names,
  endpoint paths, or code.
- Never let a PR close an issue: no `Closes` / `Fixes` / `Resolves` in the title, body, or commit messages.
  Use `Refs #<id>`. A person closes the issue after verifying, not the merge.
- Call out applicable API contract, DB migration, tenant-boundary, and generated-client impacts under reviewer notes.

## Branching And Pull Requests

One issue is one branch. Create `feat/{issue-id}` from the latest `main`, do the whole task on it, then open one pull request from that branch into `main`.

Do not create a duplicate branch or cherry-pick the work onto another branch. Keep the issue branch based on `main` and do not merge unrelated work into it.


## Rollback

- App rollback is done by redeploying a known-good commit or tag that exists on `main`.
- Database rollback follows the approved backup and restore procedure for the production environment; do not assume a specific provider or restore over newer data without explicit approval.
- Do not perform release or rollback actions without explicit approval.
